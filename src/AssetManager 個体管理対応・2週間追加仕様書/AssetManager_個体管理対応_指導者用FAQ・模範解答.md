# AssetManager 個体管理対応：指導者用FAQ・模範解答

作成日: 2026-10-20  
対応仕様書: `AssetManager_個体管理対応_2週間追加仕様書.md`  
対応ER: `AssetManager_個体管理対応_最終ER.dbml`

## 1. この資料の位置付け

この資料は、研修者の提出物を採点するときの基準と、レビュー時に深掘りするための補助資料です。コードをこの資料どおりに書くこと自体を正解にはしません。別の実装でも、次の3点を満たし、理由を説明できれば認めます。

- 資産マスタと実物個体の粒度を混ぜていない
- 同時実行・権限・履歴の整合性を壊さない
- 業務ルールをテストで再現できる

模範解答の標準方針は、仕様書とERに合わせて次のとおりです。

- `asset_items.status` に `available / loaned / repairing / disposed` を持つ案A
- `loan_histories` は `asset_item_id` を参照する
- 貸出・返却・状態変更・消耗品取得は、トランザクション内で対象行をロックする
- MySQL 8系のテスト用DBを使用する
- 「未返却1件まで」のDB制約は必須ではなく、行ロックによるアプリ保証を必須とする
- ブラウザテストは社員の貸出・返却シナリオを必須とし、権限・IDORはFeature Testで確認する

## 2. 到達目標に対する模範回答

### Q1. この課題で一番重要な設計変更は何ですか？

`assets` の1行を「資産の種類」として残し、実物1台ごとの情報を新しい `asset_items` に分けることです。

例えば「ノートPC」という資産マスタに対して、`PC-0001`、`PC-0002`、`PC-0003` という個体を持たせます。貸出履歴は「ノートPCを借りた」ではなく、「PC-0001を借りた」と記録します。

これは、同じ種類の実物を複数管理するためだけでなく、管理番号・シリアル番号・修理中・廃棄済みという個体の属性を、資産マスタの属性から分離するためです。

### Q2. `assets` に個体の列を追加するだけではいけませんか？

1台しか存在しない期間だけなら動いて見えますが、同じ種類のPCを複数台管理できません。管理番号やシリアル番号をカンマ区切りで保存する方法も、検索・一意性・貸出状態の管理が困難になり、1列1値の原則に反します。

「種類」と「実物」は粒度が異なるため、`assets` と `asset_items` を分けるのが標準解です。

### Q3. 消耗品にも個体を作りますか？

作りません。消耗品は `assets.stock` の数量で管理し、取得履歴は `consumable_histories` に残します。ボールペン1本ごとに管理番号を付ける対象ではないからです。

ただし、個体登録時に選択された資産の `asset_type` が `loan` であることはアプリケーションで検証します。外部キーだけでは、参照先が貸出資産か消耗品かまでは保証できません。

## 3. ER設計の模範解答

### 3.1 テーブルの責務

| テーブル | 責務 | 模範判断 |
| --- | --- | --- |
| `assets` | 資産の種類、消耗品の在庫 | 今回は既存構造を維持 |
| `asset_items` | 貸出資産の実物1台ごとの情報 | 新規追加 |
| `loan_histories` | 誰がどの個体をいつ借りたか | `asset_item_id` を参照 |
| `consumable_histories` | 消耗品を誰が何個取得したか | 個体管理とは分離 |

### 3.2 `loan_histories.asset_id` を残さない理由

`loan_histories.asset_item_id` から `asset_items.asset_id` をたどれば資産マスタを取得できます。両方を持つと、履歴の `asset_id` と個体の `asset_id` が異なる矛盾を許すことになります。

この課題では、同じ意味の値を複数箇所に保存して更新漏れを作らないことを優先し、旧 `asset_id` は移行完了後に削除します。

### 3.3 `status` を持つ案Aと、履歴から導出する案B

標準解は案Aです。`asset_items.status` に `loaned` を持たせることで、一覧・検索・状態表示を単純にします。ただし、未返却の `loan_histories` と同じ事実を二重に持つため、貸出と返却で必ず同一トランザクション内に両方を更新します。

案Bも設計としては成立します。案Bを選ぶ場合は、`loaned` を状態値から除外し、未返却履歴の有無を一貫して参照しなければなりません。「案Aのほうが実装しやすそう」だけでなく、検索性能、状態遷移、整合性の保証方法まで説明できることが必要です。

### 3.4 インデックスの模範判断

- `management_no` と `serial_no` は一意性と検索のためのUNIQUE
- `(asset_id, status)` は「ある資産の利用可能な個体」の検索に使う
- `(asset_item_id, return_date)` は個体の未返却履歴を探す
- `(user_id, return_date)` は社員の未返却履歴・期限超過を探す

`asset_id` 単独や `asset_item_id` 単独は、それぞれ複合インデックスの先頭列でカバーされます。`status` 単独は値の種類が少なく、単独インデックスの効果が低いので、実際の検索条件を確認せずに追加しません。

### 3.5 CHECK制約とアプリケーション検証

DBで保証する代表例は次のとおりです。

- 外部キーとNOT NULL
- 管理番号・シリアル番号の一意性
- 状態が4種類のいずれかであること
- 廃棄済みなら `disposed_on` が必須、それ以外はNULLであること

アプリケーションで保証する代表例は次のとおりです。

- `asset_type = loan` の資産だけ個体を作れる
- `available → loaned` は貸出処理だけで起こる
- `loaned → available` は返却処理だけで起こる
- `loaned` の個体に管理者が修理・廃棄を設定できない
- 未返却履歴の上限、在庫不足、貸出期限超過

アプリだけで重複を確認すると同時登録を防げないため、重複はアプリの分かりやすいエラーとDB制約の両方で守ります。

## 4. データ移行の模範解答

### Q4. なぜ `asset_item_id` を最初からNOT NULLで追加しないのですか？

既存の `loan_histories` 行には個体IDがまだないためです。既存行を埋める前にNOT NULLを付けると、DDLが失敗するか、意味のない仮値を入れる必要があります。

### Q5. 移行の標準手順は何ですか？

次の7段階です。

1. 移行前チェックSQLで、同一資産の未返却履歴が複数ないことを確認する
2. `asset_items` を作成する
3. `loan_histories.asset_item_id` をNULL可で追加する
4. 貸出資産マスタごとに `MIG-{asset_id}` の仮個体を作る
5. 既存履歴の `asset_item_id` を埋め、NULLが0件であることを確認する
6. `asset_item_id` をNOT NULLに変更する
7. 旧 `asset_id` の外部キーとカラムを削除する

移行用個体の `serial_no` は不明なのでNULLにします。仮個体であること、実物照合が必要なことを `note` に残します。

### Q6. 移行前チェックで異常が見つかったらどうしますか？

移行を止め、指導者に報告します。移行スクリプトの中で勝手に2件を1件へまとめたり、履歴を削除したりしてはいけません。これはデータの意味を推測して変更する行為だからです。

特に次の2つは0件である必要があります。

```sql
SELECT asset_id, COUNT(*) AS unreturned_count
FROM loan_histories
WHERE return_date IS NULL
GROUP BY asset_id
HAVING COUNT(*) > 1;

SELECT lh.loan_history_id
FROM loan_histories AS lh
JOIN assets AS a ON a.asset_id = lh.asset_id
WHERE a.asset_type <> 'loan';
```

### Q7. マイグレーションを1ファイルにまとめてもよいですか？

動作する場合でも、教材としては少なくとも「テーブル作成」「データ移行」「旧カラム削除」を分けるほうが望ましいです。途中の状態を確認でき、失敗箇所を特定しやすく、DB設計課題3の段階的移行を再現できるためです。

`down()` で完全に戻せない場合は、その理由をコメントに残します。旧 `asset_id` を削除した後に、実際の個体への対応関係を完全に復元できない場合があるためです。

## 5. 状態遷移の模範解答

| 現在 | 変更後 | 許可される操作 |
| --- | --- | --- |
| 新規 | `available` | 管理者の登録 |
| `available` | `loaned` | 社員の貸出だけ |
| `available` | `repairing` | 管理者の状態変更 |
| `available` | `disposed` | 管理者の状態変更 |
| `loaned` | `available` | 社員の返却だけ |
| `loaned` | `repairing` / `disposed` | 不可 |
| `repairing` | `available` | 管理者の状態変更 |
| `repairing` | `disposed` | 管理者の状態変更 |
| `disposed` | すべて | 不可 |

「貸出中から修理中・廃棄済み」を禁止する理由は、利用者の手元にある個体を管理者が状態変更すると、返却できない履歴が残るためです。「貸出中から利用可能」を管理者画面で許すと、未返却履歴を残したまま別の社員へ貸し出せます。

画面でボタンを隠すだけでは不十分です。状態遷移は、URLやPOST値を直接送られた場合にもサーバー側で再検証します。

## 6. 貸出・返却・在庫処理の模範実装方針

### 6.1 貸出

標準的な流れは次のとおりです。

1. `DB::transaction()` を開始する
2. 対象 `asset_items` を `lockForUpdate()` で取得する
3. 存在、状態が `available`、貸出可能な資産種別であることを確認する
4. 社員の期限超過など、既存の貸出条件を確認する
5. `loan_histories` を登録する
6. 個体を `loaned` に更新する
7. 成功時にCOMMIT、失敗時にROLLBACKする

状態確認と履歴登録の間にロックが必要です。トランザクションだけでは、2つの処理が同じ `available` を読んでしまいます。

### 6.2 返却

返却リクエストは履歴IDを受け取りますが、最初の読み取りだけで処理を完結させません。

1. 認証ユーザー自身の未返却履歴として対象を仮取得する
2. 履歴から個体IDを知る
3. トランザクション内で個体をロックする
4. 履歴をロック付きで取得し直す
5. まだ未返却であること、ユーザー本人の履歴であることを確認する
6. 履歴に返却日時を設定し、個体を `available` に戻す

履歴を取得し直すのは、同じ返却ボタンの二重送信などで、最初の読み取り後に別処理が先に返却を完了する可能性があるためです。ロック後の最新状態を判定に使います。

### 6.3 状態変更

管理者の状態変更は、個体をロックしてから現在状態を再確認します。`loaned` からの修理・廃棄、`disposed` からの復帰は拒否します。状態変更フォームから `status=loaned` を受け付けてはいけません。`loaned` は貸出処理だけが設定します。

### 6.4 消耗品取得

在庫確認、在庫減算、取得履歴登録を同じトランザクションで実行します。

1. 対象の `assets` 行を `lockForUpdate()` で取得する
2. 消耗品であること、数量が正数であること、在庫が足りることを確認する
3. `WHERE stock >= quantity` などの条件付きUPDATEを行う
4. 更新件数が1であることを確認する
5. 取得履歴を登録する
6. 失敗時は全体をROLLBACKする

在庫減算の前に履歴を登録すると、減算失敗時に履歴だけ残る危険があります。逆に減算だけして履歴登録に失敗すると在庫だけ減るため、両方を同一トランザクションにします。

### 6.5 ロック順序

貸出・返却・状態変更の対象個体については、原則として「個体 → 貸出履歴」の順に統一します。処理ごとに「履歴 → 個体」のように逆順にすると、同時実行時にデッドロックの原因になります。

## 7. 既存不具合6件の模範修正方針

### No.1 `LoanHistory::countOverdue()`

`where('user_id', $user)` のようにUserオブジェクトをそのまま比較せず、`$user->user_id` などの主キーを渡します。メソッドの引数をUserにするかIDにするかを決め、呼び出し側も統一します。期限超過件数を確認するFeature Testを追加します。

### No.2 `Asset::consumableAssetData()`

要発注条件は「在庫が最低在庫を下回ったとき」なので、`stock < min_stock` が標準的な意味です。カラム同士の比較には `whereColumn('stock', '<', 'min_stock')` を使います。境界値として同値の場合もテストします。

### No.3 `UsageHistoryController::returnAsset()`

対象履歴が存在し、かつログインユーザー本人の未返却履歴であることを検索条件に含めます。見つからない場合は500にせず、404または適切なエラーとして扱います。DBが更新されていないこともテストします。

### No.4 貸出制限メッセージ

7日以上の期限超過が理由なら、「すでに貸出中です」ではなく、期限超過による貸出制限であることが分かるメッセージを返します。表示文言だけでなく、制限条件のFeature Testを残します。

### No.5 資産が存在しない場合の例外

`throw new \Exception` で500画面を見せるのではなく、入力検証、`findOrFail()`、404レスポンス、または利用者向けエラーのいずれかを既存方針に合わせて選びます。内部情報やスタックトレースを画面に出さないことが重要です。

### No.6 消耗品の在庫競合

在庫チェックをトランザクション外に置かず、資産行のロック後に行います。`decreaseStock()` の戻り値が0なら在庫不足として例外または検証エラーにし、取得履歴を登録しません。テストでは、在庫数と履歴件数が失敗前後で変わらないことを確認します。

## 8. セキュリティの模範解答

### Q8. 個体登録フォームから `status=disposed` を送られたらどうしますか？

登録処理の入力項目に `status` を含めません。`$request->validated()` の値だけを使い、状態はサーバー側で常に `available` を設定します。モデルの `$fillable` に `status` を入れない方針も有効です。

### Q9. IDORはどのテストで確認しますか？

Feature Testです。社員Aの未返却履歴IDを社員Bが返却しようとするリクエストを直接送信し、拒否されることと、履歴の `return_date` がNULLのままであることを確認します。ブラウザテストでURLを書き換える必要はありません。

### Q10. CSRFをFeature Testで確認できますか？

この課題の通常のLaravel Feature Testでは、テスト実行中にCSRF検証が無効化されるため、「トークンなしなら419」をそのまま確認できません。

したがって、次を分けて確認します。

- Feature Test：対象ルートがPOST/PATCH等であること、認証・認可・入力検証を確認
- コードレビュー：各フォームに `@csrf` があることを確認
- 手動確認：ブラウザの開発者ツールでトークンを除去して送信し、419になることを記録

テストのためだけにCSRF無効化を解除する変更を加える必要はありません。手動確認の日時・対象URL・結果をテスト観点表に残します。

### Q11. XSSの確認方法は？

管理番号や備考に `<script>alert(1)</script>` を登録し、Bladeの `{{ }}` 出力によってHTML上でエスケープされることを確認します。`{!! !!}` を使っている箇所があれば、HTMLを許可する明確な理由がない限り修正します。

### Q12. LIKE検索で何をエスケープしますか？

`\`、`%`、`_` を検索文字列中のリテラルとして扱えるようにエスケープします。`PC_0001` と `PCX0001` を用意し、`PC_` の検索で前者だけがヒットするテストを期待します。単に `addslashes()` を使うのではなく、使用するDBとLIKEのESCAPE指定に合った実装にします。

## 9. テストの模範解答

### 9.1 必須ファクトリ

最低限、次を用意します。

- `AssetFactory`：貸出資産・消耗品の状態を作れる
- `LoanCategoryFactory`
- `AssetItemFactory`：`available`、`loaned`、`repairing`、`disposed` の状態を作れる
- `LoanHistoryFactory`：未返却・返却済み・期限超過を作れる
- `UserFactory`：管理者・一般社員を作れる

ファクトリはテストデータを短くするためだけでなく、テストが「何の状態を作っているか」を明確にするために作ります。

### 9.2 Unit Testの期待項目

- `available` は貸出可能
- `loaned`、`repairing`、`disposed` は貸出不可
- `available → repairing` は許可
- `available → disposed` は許可
- `repairing → available` は許可
- `repairing → disposed` は許可
- `loaned → repairing` は拒否
- `loaned → disposed` は拒否
- `disposed` からの変更は拒否

### 9.3 Feature Testの期待項目

| 観点 | 成功条件 |
| --- | --- |
| 管理者の個体登録 | 登録され、状態は`available` |
| 一般社員の管理者URL | 拒否され、個体は変更されない |
| 消耗品を個体登録 | バリデーションエラー |
| 管理番号重複 | エラーになり、2件目は保存されない |
| 貸出 | 履歴が増え、個体が`loaned` |
| 修理中の貸出 | 拒否され、履歴が増えない |
| 返却 | 自分の未返却履歴だけが返却済みになる |
| 他人の履歴返却 | 拒否され、履歴は未返却のまま |
| 状態変更の不正POST | サーバー側で拒否される |
| CSRF以外の入力検証 | 不正値で保存されない |
| ワイルドカード検索 | `%`や`_`が検索記号として悪用されない |
| XSS | 出力がエスケープされる |
| 消耗品在庫不足 | 在庫・履歴ともに不変 |

### 9.4 同時実行テスト

`lockForUpdate()` の存在だけをモックして確認するのでは不十分です。MySQLのテスト用DBで、同じ個体に対する2処理のうち一方がロック解放を待ち、解放後に最新状態を再確認して失敗することを確認します。

「先に読んだ時点ではavailableだった」ことを根拠に2件目を成功させていないかを見ます。発展課題の生成列＋UNIQUEを実装した場合でも、アプリ側の状態確認と分かりやすいエラー処理は必要です。

### 9.5 ブラウザテストの必須シナリオ

Laravel Duskを標準とします。導入に半日を超える場合は指導者へ相談し、Feature Testを先に完成させます。

必須シナリオは次の1本です。

1. 社員としてログインする
2. 利用可能な個体が表示されることを確認する
3. 個体を選んで貸出する
4. 貸出中の表示と利用履歴を確認する
5. 返却する
6. 利用可能に戻ったことを確認する

管理者の登録・編集・状態変更は発展シナリオです。権限、IDOR、CSRFなし、異常なPOST値はFeature Testまたは手動確認で扱います。

## 12. 指導者向け補足

### Q13. 案Aは冗長なので不正解ではありませんか？

不正解ではありません。導出可能な値を保存することには矛盾のリスクがありますが、一覧検索を単純にし、状態を明示的に扱える利点があります。この課題では、二重管理の危険をトランザクションと行ロックで管理することを学習目標にしているため、案Aを標準としています。

### Q14. `loaned` を管理者が直接設定できないのはなぜですか？

`loaned` は「未返却の貸出履歴が存在する」という業務事実と結びついているためです。状態だけ変更すると履歴との矛盾が生じます。管理者が現物の状態を変更する画面では、`available / repairing / disposed` の遷移だけを扱います。

### Q15. 返却済み履歴を削除してもよいですか？

原則として削除しません。履歴は監査・利用状況・期限超過確認のために残します。返却は `return_date` の更新で表現します。

### Q16. `serial_no` が空欄の個体を複数登録できるのはなぜですか？

NULLは「値が不明・未登録」を表し、MySQLのUNIQUEでは複数のNULLが許容されるためです。空文字のまま保存すると同じ値として扱われる可能性があるため、空文字をNULLに変換する挙動を確認します。

### Q17. `acquired_at` ではなく `acquired_on` とした理由は？

`date` 型であり、時刻を持たないことを名前から分かるようにするためです。必須の命名規則ではありませんが、`created_at` などの日時列との誤解を避けます。

### Q18. CSRFを自動テストできないなら、要件から外してよいですか？

外しません。自動テストできない範囲があること自体を理解する課題です。フォームのトークン、手動の419確認、認証・認可のFeature Testを組み合わせて確認します。
