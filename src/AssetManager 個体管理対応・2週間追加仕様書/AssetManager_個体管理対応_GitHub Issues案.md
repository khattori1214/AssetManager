# AssetManager 個体管理対応：GitHub Issues案

対応仕様書：`AssetManager_個体管理対応_2週間追加仕様書.md`

## 使い方

以下の各セクションを、GitHub Issueを作成するときの本文として使用する。

- Issueタイトルをタイトル欄に設定する
- 本文をIssue本文へ貼り付ける
- ラベルとマイルストーンを設定する
- 完了条件をすべて確認してからIssueをクローズする

想定するラベル：`研修`、`設計`、`実装`、`テスト`、`セキュリティ`、`レビュー`、`必須`、`発展`

## Issue 1：現在の貸出機能を調べ、改修前の動きを記録する

**ラベル**：`研修` `調査` `テスト` `必須`  
**目安**：1〜2日目  
**依存**：なし

### 目的

現在のAssetManagerが、貸出・返却・消耗品取得をどのように処理しているかを理解する。改修後に既存機能が壊れていないか比較できるようにする。

### やること

- 貸出・返却・消耗品取得に関係するコードを読む
- `asset_id` を使っている場所を探す
- 改修前の貸出・返却・消耗品取得をテストする
- 既存不具合を再現して結果を記録する
- MySQLのテスト用DBでテストを実行できるようにする

### 完了条件

- 影響範囲表が作成されている
- 改修前の主要機能を確認するテストがある
- 既存不具合の再現結果が記録されている
- テスト用DBを使ってテストを実行できる
- 研修者が「どの処理を変更する必要があるか」を説明できる

非コード成果物の模範解答は、`AssetManager_個体管理対応_非コーディング成果物_模範解答.md` の「1」を参照する。

## Issue 3：既存の貸出履歴を個体管理へ移行する

**ラベル**：`設計` `実装` `DB` `必須`  
**目安**：4〜5日目  
**依存**：Issue 2

### 目的

既存の貸出履歴を失わずに、資産マスタ単位の管理から個体単位の管理へ変更する。

### やること

- 移行前チェックを行う
- `asset_items` を追加する
- 既存の貸出履歴に個体を割り当てる
- `loan_histories` の参照先を変更する
- モデル・リレーション・シーダーを修正する
- 開発DBで移行を実行する

### 完了条件

- 移行前チェックの結果が記録されている
- 既存履歴を残したままマイグレーションが実行できる
- 既存履歴が`asset_item_id`を参照している
- 移行用の仮個体が仮登録だと分かる
- 移行後に旧`loan_histories.asset_id`が不要になっている
- 空のDBと既存データの両方でマイグレーションを確認している

移行前チェックで問題が見つかった場合は、勝手にデータを修正せず指導者に相談する。

非コード成果物の模範解答は、`AssetManager_個体管理対応_非コーディング成果物_模範解答.md` の「3」を参照する。

## Issue 4：管理者が資産個体を管理できるようにする

**ラベル**：`実装` `テスト` `必須`  
**目安**：5〜7日目  
**依存**：Issue 3

### 目的

管理者が、実物1台ごとの情報を登録・検索・確認・編集できるようにする。

### やること

- 個体登録を実装する
- 個体一覧・詳細を実装する
- 資産名・管理番号・シリアル番号・状態で検索できるようにする
- 個体編集を実装する
- 状態変更を実装する
- 管理者権限を確認する
- 状態遷移のテストを作成する

### 完了条件

- 管理者が貸出資産に個体を登録できる
- 消耗品には個体を登録できない
- 登録時の状態は`available`になる
- 一般社員は管理者機能を利用できない
- 状態遷移のルールが守られる
- 一覧・詳細・編集・検索が動作する
- 状態を不正な値に変更できない

## Issue 5：個体単位で貸出・返却できるようにする

**ラベル**：`実装` `テスト` `必須`  
**目安**：8〜9日目  
**依存**：Issue 3、Issue 4

### 目的

資産の種類ではなく、実物の個体を選んで貸出・返却できるようにする。

### やること

- 個体を選んで貸出できるようにする
- 貸出履歴が個体を参照するようにする
- 貸出中・修理中・廃棄済みの個体を貸出できないようにする
- 自分の貸出だけ返却できるようにする
- 返却後に個体を利用可能へ戻す
- 既存の貸出・返却画面を修正する

### 完了条件

- 個体単位で貸出できる
- 貸出すると個体が`loaned`になる
- 返却すると履歴が返却済みになり、個体が`available`になる
- 他人の履歴を返却できない
- 同じ履歴を二重に返却できない
- 既存の貸出・返却の主要な動作が改修前と同じように動く

## Issue 6：同時操作でデータが壊れないようにする

**ラベル**：`実装` `DB` `テスト` `必須`  
**目安**：Issue 5と並行して8〜9日目  
**依存**：Issue 3、Issue 4、Issue 5

### 目的

同じ個体を2人が同時に借りたり、在庫を超えて消耗品を取得したりする問題を防ぐ。

### やること

- 貸出処理をトランザクション内で行う
- 対象個体をロックしてから状態を確認する
- 返却・状態変更にも同じ考え方を適用する
- 消耗品の在庫確認と減算を安全にする
- ロックを取る順番を整理する

### 完了条件

- トランザクションだけでは二重貸出を防げない理由を説明できる
- 貸出・返却・状態変更・消耗品取得で排他制御を行っている
- 同じ個体に対する同時貸出で、成功するのが1件だけになる
- 在庫不足時に取得履歴だけが残らない
- 個体と貸出履歴の状態が矛盾しない
- ロックの取得順序を説明できる

非コード成果物の模範解答は、`AssetManager_個体管理対応_非コーディング成果物_模範解答.md` の「6」を参照する。

## Issue 7：セキュリティと既存不具合を確認する

**ラベル**：`セキュリティ` `テスト` `必須`  
**目安**：10日目  
**依存**：Issue 4、Issue 5、Issue 6

### 目的

画面に表示されていない操作や不正なIDを送られても、安全に動作するようにする。

### やること

- 認証・認可を確認する
- IDORを確認する
- マスアサインメントを確認する
- XSSを確認する
- CSRFを確認する
- LIKE検索のワイルドカードを確認する
- 既存不具合6件を修正する

### 完了条件

- 一般社員が管理者機能を利用できない
- 他人の貸出履歴を操作できない
- リクエストの`status`で個体状態を不正変更できない
- 入力値が画面上でHTMLとして実行されない
- CSRFトークンなしのPOSTが419になることを手動確認している
- `%`や`_`を使った検索が意図しない全件検索にならない
- 既存不具合6件について、修正前後のテスト結果がある

## 遅れた場合の扱い

次の順番で発展要素を後回しにする。

1. 管理者のブラウザテスト
2. ブラウザテストの異常系
3. 個体状態の変更履歴
4. 生成列＋UNIQUEによる未返却履歴のDB保証
5. 本番相当データでの移行リハーサル

以下は後回しにしない。

- 改修前の特性テスト
- データ移行
- 貸出・返却の行ロック
- IDORと認可の確認
- 社員の貸出・返却ブラウザテスト
