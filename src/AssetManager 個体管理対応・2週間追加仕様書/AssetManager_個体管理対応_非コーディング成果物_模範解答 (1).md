# AssetManager 個体管理対応：非コーディング成果物の模範解答

この資料は、GitHub Issueの完了条件のうち、表・設計資料・確認記録など、コード以外の成果物に対する模範例である。

完全に同じ表現でなくても、理由と確認方法が説明できていればよい。特に現在の実装に依存する箇所は、実際に調査した結果を優先する。

## 1. Issue 1：影響範囲表の模範解答

| 確認項目 | 現在の実装 | 個体管理後の変更 |
|---|---|---|
| 貸出対象の識別 | 貸出リクエストが`asset_id`を受け取る | `asset_item_id`を受け取る |
| 貸出中の判定 | `loan_histories`の未返却履歴を資産マスタ単位で確認 | 個体の`status`と未返却履歴を確認 |
| 貸出履歴の参照先 | `loan_histories.asset_id` | `loan_histories.asset_item_id` |
| 貸出可能表示 | 資産マスタ単位で貸出可否を表示 | 利用可能な個体を表示 |
| 貸出処理 | `AssetApplicationController::borrow()` | 個体をロックし、履歴登録と`status`変更を同一処理で行う |
| 返却処理 | `UsageHistoryController::returnAsset()` | 自分の未返却履歴を取得し、個体をロックして返却する |
| 利用履歴の資産名 | 履歴から`assets`を参照 | `loan_histories → asset_items → assets` とたどる |
| 管理者の貸出状況 | 資産マスタ単位 | 個体単位で利用者を表示 |
| シーダー | `LoanHistorySeeder`が`asset_id`を利用 | 個体を作成して`asset_item_id`を利用 |
| 消耗品取得 | `assets.stock`を減算し取得履歴を登録 | 個体管理とは分離し、在庫行をロックする |
| 状態変更 | 個体状態は未対応 | 管理者が`available / repairing / disposed`を変更する |

### 調査時の注意

この表は推測で埋めず、次の検索結果と対応付ける。

- `asset_id`
- `loan_histories`

## 2. Issue 2：設計判断の模範解答

### 2.1 テーブルの責務

| テーブル | 管理するもの |
|---|---|
| `assets` | 「ノートPC」「モニター」など資産の種類、消耗品の在庫 |
| `asset_items` | `PC-0001`など実物1台ごとの管理番号・シリアル番号・状態 |
| `loan_histories` | 誰がどの個体をいつ借り、いつ返却したか |
| `consumable_histories` | 誰が消耗品を何個取得したか |

### 2.2 `status`を持つ案を選ぶ理由

標準解は、`asset_items.status`に`loaned`を持たせる案Aである。

理由は、個体一覧で状態を表示しやすく、利用可能な個体の検索も単純になるためである。一方で、未返却の`loan_histories`と同じ事実を二重に持つため、貸出・返却では必ず同じトランザクション内で両方を更新する。

案Bを採用しなかった理由は、一覧・検索のたびに未返却履歴を確認する必要があり、今回の研修では実装が複雑になるためである。ただし、案Bも設計としては成立する。

### 2.3 状態遷移図の模範

```text
新規登録 ──> available
                │  ├──> repairing ──> available
                │  │                     │
                │  │                     └──> disposed
                │  ├──> disposed
                │  └──> loaned ──> available

disposed からの状態変更は禁止
loaned から repairing / disposed への変更は禁止
```

### 2.4 業務ルールと保証場所

| 業務ルール | 保証場所 | 理由 |
|---|---|---|
| 個体は資産マスタに属する | DBのFKとアプリ | FKは存在を保証し、貸出資産かどうかはアプリで確認する |
| 管理番号は重複しない | DBのUNIQUE＋アプリ | DBで同時登録を防ぎ、アプリで分かりやすいエラーを返す |
| 状態は4種類だけ | DBのCHECK＋アプリ | DBと入力検証の両方で不正値を防ぐ |
| 廃棄済みなら廃棄日が必要 | DBのCHECK | どの登録経路からでも守る必要がある |
| 貸出中は未返却履歴が1件ある | アプリ |複数テーブルの関係と同時実行を扱うため |
| 貸出中の個体を廃棄できない | アプリ | 状態遷移の業務ルールだから |
| 消耗品の在庫を超えて取得できない | アプリ＋トランザクション | 残数確認と減算を同時に行う必要がある |

## 3. Issue 3：移行成果物の模範解答

### 3.1 移行手順

1. 移行前チェックSQLを実行する
2. `asset_items`を作成する
3. `loan_histories.asset_item_id`をNULL可で追加する
4. 貸出資産ごとに`MIG-{asset_id}`の仮個体を作成する
5. 既存履歴に`asset_item_id`を設定する
6. NULLの履歴が0件であることを確認する
7. `asset_item_id`をNOT NULLにし、旧`asset_id`を削除する

### 3.2 移行用個体の設定

| 項目 | 模範値 | 理由 |
|---|---|---|
| `management_no` | `MIG-12` | 移行で作られた仮個体だと分かる |
| `serial_no` | `NULL` | 不明な情報を推測しない |
| `status` | 未返却履歴があれば`loaned`、なければ`available` | 現在の貸出状況を引き継ぐ |
| `note` | `データ移行時に仮登録。実物との照合が必要` | 仮登録であることを残す |

### 3.3 移行前チェックの期待結果

次の2つのSQLは、原則として0件になることを確認する。

```sql
SELECT asset_id, COUNT(*) AS unreturned_count
FROM loan_histories
WHERE return_date IS NULL
GROUP BY asset_id
HAVING COUNT(*) > 1;
```

```sql
SELECT lh.loan_history_id, a.asset_id, a.asset_type
FROM loan_histories AS lh
JOIN assets AS a ON a.asset_id = lh.asset_id
WHERE a.asset_type <> 'loan';
```

0件でない場合の模範対応は、「移行を止め、データの意味を確認してから方針を決める」である。履歴を勝手に削除したり、複数人の貸出を1個体にまとめたりしない。

### 3.4 移行後の確認項目

- 旧履歴件数と移行後履歴件数が一致している
- `asset_item_id IS NULL`の履歴が0件である
- 各履歴の個体が元の資産マスタに属している
- 未返却履歴を持つ仮個体が`loaned`になっている
- 移行用個体の備考に仮登録であることが残っている
- 旧`asset_id`を参照するアプリコードが残っていない

## 5. Issue 5：貸出・返却の確認シナリオ

### 貸出

1. 利用可能な個体を1件用意する
2. 社員がその個体を貸出する
3. 貸出履歴が1件増える
4. 個体の状態が`loaned`になる
5. 別の社員が同じ個体を借りられない

### 返却

1. 社員Aの未返却履歴を1件用意する
2. 社員Aが返却する
3. 履歴に返却日時が入る
4. 個体が`available`になる
5. 社員Bが社員Aの履歴IDを使って返却できない
6. 同じ履歴を2回返却しても、2回目はDBを変更しない

## 6. Issue 6：排他制御の説明資料の模範解答

### 6.1 トランザクションだけでは足りない理由

トランザクションは、処理を全部成功させるか全部取り消すかを保証する。しかし、ロックなしで2つの処理が同じ`available`を読むことは防げない。

そのため、次のような二重貸出が起きる。

```text
処理A：個体を読む → available
処理B：個体を読む → available
処理A：履歴登録、loanedへ変更、COMMIT
処理B：履歴登録、loanedへ変更、COMMIT
```

### 6.2 ロック対象

| 処理 | ロック対象 | 防ぐ問題 |
|---|---|---|
| 貸出 | 対象個体 | 同じ個体の二重貸出 |
| 返却 | 対象個体、対象履歴 | 二重返却 |
| 状態変更 | 対象個体 | 貸出中の個体を状態変更 |
| 消耗品取得 | 対象資産 | 在庫超過 |

### 6.3 ロック順序

基本の順序は「個体 → 貸出履歴」で統一する。

返却では最初に履歴を読まないと個体IDが分からないため、最初の読み取りはロックなしで行う。その後、トランザクション内で個体をロックし、履歴を取得し直して最新状態を確認する。

## 7. Issue 7：セキュリティ確認記録の模範

| 観点 | 確認方法 | 期待結果 |
|---|---|---|
| 認可 | 一般社員で管理者URLへアクセス | 拒否される |
| IDOR | 他人の履歴IDで返却POST | 拒否され、DB不変 |
| マスアサインメント | 登録POSTに`status=disposed`を追加 | `available`で登録される |
| XSS | 備考に`<script>`を登録して表示 | スクリプトが実行されず、文字列がエスケープされる |
| CSRF | `_token`を削除してブラウザ送信 | 419になる |
| LIKE | `PC_`で検索 | `_`をワイルドカードとして扱わない |
| 状態遷移 | `loaned`を`repairing`へ直接POST | 拒否される |

CSRFだけは、通常のFeature Testではなく、フォーム確認とブラウザの手動操作結果を記録する。

## 8. Issue 8：テスト観点表とREADMEの模範

### 8.1 テスト観点表

| 分類 | 観点 | テスト方法 | 期待結果 |
|---|---|---|---|
| 正常 | 管理者が個体を登録 | Feature Test | `available`で登録される |
| 正常 | 利用可能な個体を貸出 | Feature Test | 履歴登録、状態`loaned` |
| 正常 | 自分の貸出を返却 | Feature Test | 返却日時設定、状態`available` |
| 異常 | 修理中の個体を貸出 | Feature Test | 拒否、DB不変 |
| 異常 | 他人の履歴を返却 | Feature Test | 拒否、DB不変 |
| 異常 | 貸出中から廃棄 | Unit/Feature Test | 拒否 |
| 異常 | 消耗品の在庫超過 | Feature Test | 履歴・在庫ともに不変 |
| 同時実行 | 同じ個体を同時に貸出 | MySQL検証 | 成功は1件だけ |
| セキュリティ | CSRFなしPOST | 手動確認 | 419 |
| 画面 | 社員の貸出・返却 | Dusk | 画面操作が最後まで成功 |

### 8.2 READMEに書く内容

```text
1. テスト用DBを作成する
2. .env.testingでテストDBを指定する
3. マイグレーションを実行する
4. PHPUnitを実行する
5. Duskを実行する
6. テストが失敗した場合に確認するログを確認する
```

READMEには実際のプロジェクトで使用するコマンドを記載する。コマンドを実行していない状態で推測して書かない。
